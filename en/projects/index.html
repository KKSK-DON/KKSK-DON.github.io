A few AI-infrastructure projects, covering inference, distributed communication, training performance, and CUDA kernels.

INT8 KV-Cache Quantization for vLLM

Personal vLLM fork — PyTorch, vLLM v1 paged attention & KV-cache internals, lm-eval

  • Overview: Designed and implemented dynamic and static INT8 KV-cache quantization: analyzed KV value distributions and quantization error to pick per-channel granularity; built a quantized PagedAttention operator and its tests in PyTorch, validated accuracy with dynamic quantization first, then designed the static scheme on top of it. Dynamic mode computes scales at runtime and quantizes KV on read; static mode calibrates fixed scales offline and loads them, with vLLM’s KV-cache allocation and read/write paths reworked to quantize on write and store INT8.
  • Accuracy: Static quantization matches the BF16 baseline on full GSM8K and HumanEval; compatible with chunked prefill and prefix caching.
  • Capacity: Static quantization halves the per-token KV footprint, doubling KV-cache capacity at the same memory budget and raising the prefix-cache hit rate.

Multimodal Training Performance Optimization

torch.profiler, pinned memory + CUDA events, operator fusion

  • Overview: Profiled and optimized multi-GPU training of an open-source multimodal model: captured traces with torch.profiler, then located and removed sync points, fused small kernels, and overlapped communication with compute; verified by comparing baseline and optimized traces.
  • Sync-point removal: Switched H2D data copies to pinned memory + non_blocking so the CPU returns as soon as the copy is issued; for GPU results the CPU has to read, copy them into pinned memory with non_blocking, record a CUDA event, and synchronize only at the point of use; replaced the forward-pass .item() with a value computed ahead of time and passed in; GPU idle time per step down by about 8 ms.
  • Operator fusion: Replaced RMSNorm and RoPE with Apex FusedRMSNorm and TransformerEngine FusedRoPE: one RMSNorm call drops from 8 kernels to 1 (218.7 µs → 35.7 µs), RoPE from 10 to 2; kernels per step 21761 → 14008, elementwise small-kernel GPU time −30%.
  • Communication–compute overlap: Analyzed how all-gather overlaps with compute and found the forward-pass all-gather serialized behind an independent multimodal encoding step; moved that encoding onto its own CUDA stream so the two overlap, with an event wait at first use to keep results correct, saving about 3 ms per step.

MoE All-to-All Dispatch/Combine, DeepEP-Aligned

PyTorch distributed — expert parallelism, variable-length all-to-all

  • Overview: Implemented a DeepEP-equivalent MoE expert-parallel dispatch and combine from scratch on torch.distributed all_to_all_single, covering the full expert-parallel flow.
  • Communication: Cut per-layer communication from the reference implementation’s 5 all-to-all rounds to 3 (one expert-count exchange plus two variable-length data exchanges): using the transpose symmetry of the send/receive matrix, the return-trip splits and other counts are derived locally instead of exchanged again.
  • Validation: Compared against DeepEP V2 on a two-GPU NVLink H100 node: combine outputs match; with DeepEP’s deterministic mode on, dispatch outputs match row for row as well.

Hand-Written CUDA Kernels

CUDA C++ — Nsight Compute

  • Overview: Wrote LayerNorm/RMSNorm, GEMM, reduce, and other FP32 kernels and optimized them step by step on H100, verifying accuracy against cuBLAS and CPU references; classified each kernel as bandwidth- or compute-bound from its arithmetic intensity, and used Nsight Compute to analyze bandwidth and compute utilization and pin down bottlenecks.
  • LayerNorm/RMSNorm: Techniques used: tree reduction → warp-shuffle reduction → two-level reduction; float4 vectorized memory access; register caching; bandwidth utilization LayerNorm 63.8% → 81.3%, RMSNorm 46.5% → 81.7%.
  • GEMM: Step-by-step optimization: coalesced access → shared-memory tiling → 1D/2D thread tiles with register reuse → float4 vectorized loads and stores → double buffering; with 128×128 tiles, 58% FP32 compute utilization, 75% of cuBLAS.
